ApiX چیست؟
ApiX یک محیط توسعه و آزمایش API برای اندروید است. با آن می‌توانی بدون نیاز به کامپیوتر، درخواست‌های شبکه را بسازی و بفرستی، احراز هویت را تنظیم کنی، پاسخ سرور را بررسی کنی، تست خودکار بنویسی، چند درخواست را به هم زنجیر کنی و رفتار API را از نظر خطا، امنیت و کارایی ارزیابی کنی.

درخواست‌های اصلی REST و GraphQL از موتور شبکه نیتیو اندروید (OkHttp) ارسال می‌شوند؛ رابط فعلی برنامه در WebView اجرا می‌شود.


۱. ارسال درخواست و پروتکل‌ها
• REST API: ارسال متدهای GET، POST، PUT، PATCH، DELETE، HEAD و OPTIONS به آدرس دلخواه.
• GraphQL: اجرای Query و Mutation، تعیین نام عملیات و Variables، دریافت Schema با Introspection و مرور نوع‌ها و فیلدها.
• WebSocket: اتصال به نشانی‌های ws و wss، ارسال و دریافت پیام زنده، تنظیم هدر و احراز هویت، Ping/Pong و اتصال مجدد.
• درخواست‌های هم‌زمان: باز نگه‌داشتن چند درخواست در تب‌های جداگانه و حفظ وضعیت هر تب.


۲. ساخت و تنظیم درخواست
• تعیین آدرس، متد و پارامترهای Query.
• افزودن، ویرایش و حذف Headerهای دلخواه.
• احراز هویت با Bearer Token، Basic Auth و API Key.
• ارسال بدنه با فرمت JSON، متن خام و فرم URL Encoded.
• آپلود فایل و تنظیم نوع محتوای درخواست.
• وارد کردن درخواست آماده از cURL یا تعریف API از Swagger/OpenAPI.


۳. محیط‌ها و متغیرها
برای محیط‌هایی مانند Development، Test و Production متغیر بساز. متغیرها را در URL، پارامترها، Headerها، احراز هویت و بدنه درخواست استفاده کن تا هنگام جابه‌جایی محیط، لازم نباشد آدرس‌ها و توکن‌ها را دستی عوض کنی. محیط‌ها امکان خروجی گرفتن و وارد کردن مستقل دارند.


۴. پاسخ، تاریخچه و مجموعه‌ها
• مشاهده وضعیت HTTP، زمان پاسخ، Headerها و بدنه پاسخ در نماهای JSON، Raw و Headers.
• جست‌وجو در پاسخ و مقایسه ساختاریافته دو پاسخ JSON.
• ثبت تاریخچه درخواست‌ها و پاسخ‌ها.
• ذخیره درخواست‌ها در پوشه‌ها و مجموعه‌های تو در تو.
• اجرای درخواست‌های یک مجموعه به‌ترتیب و دریافت گزارش موفقیت و خطا.
• انتقال مجموعه‌ها با فایل JSON و تهیه نسخه پشتیبان کامل از داده‌های برنامه.


۵. اسکریپت و تست خودکار
• اجرای اسکریپت پیش‌درخواست برای آماده‌سازی درخواست REST.
• نوشتن تست برای بررسی وضعیت، Header و داده‌های پاسخ در REST و GraphQL.
• استفاده از متغیرها و خروجی مراحل قبلی در درخواست‌های بعدی.
• ساخت Assertion برای مقایسه مقدارها و اعتبارسنجی نتیجه.
• اجرای سناریوهای چندمرحله‌ای با شرط، استخراج داده و گزارش اجرا.
• اعتبارسنجی پاسخ JSON با JSON Schema به‌صورت آفلاین.


۶. ابزارهای تخصصی
• تولید کد: تبدیل درخواست به JavaScript Fetch، Python Requests یا PHP cURL.
• JWT Decoder: نمایش Header و Payload توکن؛ این ابزار امضای توکن را اعتبارسنجی نمی‌کند.
• Cookie Manager: مشاهده و مدیریت کوکی‌های HTTP ذخیره‌شده و ارسال خودکار آن‌ها در درخواست‌های بعدی.
• Mock Server: ساخت API آزمایشی روی خود گوشی برای تعریف مسیر، متد، کد وضعیت و پاسخ دلخواه؛ این سرور به‌طور پیش‌فرض روی 127.0.0.1 در دسترس است و عمومی نیست.
• API Monitoring: بررسی دوره‌ای در دسترس بودن API و ثبت زمان پاسخ و قطعی‌ها؛ پایش تا وقتی برنامه فعال است ادامه دارد.
• Load Testing: اجرای تست فشار با تعداد درخواست و هم‌زمانی محدود و مشاهده آمار، از جمله P95.
• Security Assessment: ارزیابی غیرویرانگر HTTPS، هدرها، کوکی‌ها، افشای فناوری، متدهای HTTP و CORS؛ آزمون‌های تزریق SQL و XSS هنوز در این نسخه پیاده‌سازی نشده‌اند؛ بررسی دسترسی با دو توکن و درخواست GET غیرمخرب انجام می‌شود.
• Response Search و گزارش‌ها: جست‌وجوی داده در پاسخ‌ها، ثبت اجراها و مقایسه نتایج تست.


۷. آزمایش CORS؛ چه چیزی را بررسی می‌کند؟
CORS سیاست امنیتی مرورگر است. وقتی یک صفحه وب از یک مبدأ به APIای با مبدأ دیگر درخواست می‌فرستد، مرورگر ممکن است پیش از درخواست اصلی یک درخواست آزمایشی OPTIONS بفرستد تا از سرور اجازه متد و Headerهای موردنیاز را بگیرد.

نکته مهم درباره ApiX: خود ApiX یک برنامه اندرویدی است و برای ارسال درخواست‌های اصلی خود به یک دامنه میزبانی‌شده نیاز ندارد. درخواست‌های REST و GraphQL آن با OkHttp نیتیو ارسال می‌شوند؛ بنابراین محدودیت CORS مرورگر روی این درخواست‌ها اعمال نمی‌شود. ابزار CORS در ApiX رفتار سرور را برای یک مرورگر فرضی شبیه‌سازی و پاسخ پیش‌بررسی را تحلیل می‌کند؛ این ابزار CORS را به درخواست‌های خود ApiX تحمیل نمی‌کند.

روش پر کردن ورودی‌ها:
۱. آدرس API: نشانی Endpoint سروری که باید درخواست OPTIONS را دریافت کند؛ مثلاً https://api.example.com/users.
۲. مبدأ شبیه‌سازی‌شده (Origin): نشانی صفحه یا برنامه وبی که فرض می‌کنیم می‌خواهد API را فراخوانی کند؛ این آدرس، Endpoint نیست. برای نمونه https://app.example.com.
۳. متد درخواست اصلی: متدی که مرورگر بعد از موفقیت پیش‌بررسی قصد دارد اجرا کند؛ مثل POST یا DELETE.
۴. هدرهای درخواست اصلی: نام Headerهایی که درخواست اصلی قرار است بفرستد؛ مثل authorization و content-type. این‌ها Headerهای درخواستی‌اند، نه Headerهای پاسخ سرور.
۵. کوکی و اعتبارنامه: اگر درخواست اصلی قرار است با اعتبارنامه ارسال شود، این گزینه را فعال کن تا الزام Access-Control-Allow-Credentials نیز بررسی شود.

اگر برنامه وب روی سرور ندارم چه Origin وارد کنم؟ برای آزمایش، لازم نیست سایت واقعی داشته باشی. می‌توانی از مبدأهای نمونه مانند http://localhost یا http://127.0.0.1 استفاده کنی، یا برای سناریوهای مبدأ opaque مقدار null را وارد کنی. این مقادیر فقط مبدأ فرضی مرورگر هستند و به معنی اجرای سایت یا سرور روی گوشی نیستند. از مبدأ دلخواه نیز می‌توانی برای شبیه‌سازی یک دامنه واقعی استفاده کنی.

هدرهای Origin، Access-Control-Request-Method و Access-Control-Request-Headers توسط ابزار ساخته می‌شوند. سپس پاسخ OPTIONS از نظر کد وضعیت، Access-Control-Allow-Origin، متدها، Headerها، اعتبارنامه، Vary و تغییرمسیر بررسی می‌شود. اگر Origin و Endpoint هم‌مبدأ باشند، ابزار هشدار می‌دهد که سناریوی Cross-Origin واقعی را بررسی نمی‌کنی.

محدودیت: همه درخواست‌های مرورگر Preflight ندارند؛ برخی درخواست‌های ساده بدون OPTIONS ارسال می‌شوند. این ابزار پاسخ Preflight را می‌سنجد و جای اجرای واقعی صفحه در مرورگر را نمی‌گیرد. خطای DNS، TLS، فایروال یا شبکه نیز لزوماً به معنی رد شدن CORS نیست.


۸. موتور شبکه و محدودیت‌های امنیتی
نیتیو بودن موتور شبکه به معنی دسترسی نامحدود نیست. احراز هویت، مجوزهای API، IP Allowlist، فایروال، محدودیت نرخ، TLS و سامانه‌های ضدربات همچنان می‌توانند درخواست را رد کنند. نتیجه تست‌ها را با توجه به محیط و مجوز دسترسی تفسیر کن.


ApiX ابزار توسعه و عیب‌یابی است، نه مجوز دسترسی به سرویس‌ها. درخواست‌ها و تست فشار را فقط روی سرویس‌هایی اجرا کن که مالک آن‌ها هستی یا اجازه آزمایششان را داری. از توکن‌ها، رمزها و اطلاعات محرمانه محافظت کن. بکاپ‌ها ممکن است شامل اطلاعات حساس باشند.

Security Assessment ارزیابی امنیتی فعال و غیرمخرب API
فاز اول ارزیابی امنیت ApiX شامل بررسی HTTPS، هدرها، کوکی‌ها، افشای فناوری، متدهای HTTP و پیش‌بررسی CORS است. این فاز علاوه بر بررسی‌های پایه، آزمون کنترل دسترسی بدون تغییر داده را با دو توکن آزمایشی فراهم می‌کند. آزمون‌های تزریق SQL و XSS هنوز اجرا نمی‌شوند.
آزمون کنترل دسترسی فقط با GET و بدون تغییر داده انجام می‌شود. برای بررسی، دو توکن آزمایشی با نقش/مالک متفاوت وارد کن. توکن‌ها ذخیره نمی‌شوند.
پس از تأیید محدوده، ارزیابی را اجرا کن.
پشتیبان‌گیری و بازیابی کامل Full Backup & Restore
از تمام داده‌های ApiX یک فایل JSON مستقل تهیه کن. فایل را در پوشه دلخواه، از جمله Download، ذخیره کن و هر زمان لازم بود با انتخاب همان فایل اطلاعات را بازیابی کن.

توجه: بازیابی، داده‌های فعلی برنامه را با محتوای فایل انتخاب‌شده جایگزین می‌کند. قبل از ادامه مطمئن شو فایل بکاپ متعلق به ApiX و نسخه موردنظرت است.

آزمایش پیش‌بررسی CORS بررسی مجوز دسترسی مبدأ


این ابزار بررسی می‌کند آیا سرور اجازه می‌دهد یک وب‌سایت مشخص، متد و هدرهای موردنظر را به کار ببرد یا نه. درخواست آزمایشی از موتور نیتیو اندروید فرستاده می‌شود؛ بنابراین محدودیت CORS مرورگر روی خود ApiX اعمال نمی‌شود.



 

 
آدرس وب‌سایتی را وارد کن که قرار است API را فراخوانی کند؛ فقط پروتکل و دامنه، بدون مسیر یا اسلش انتهایی.

 

  

  
نام هدرها را با ویرگول جدا کن؛ فقط هدرهایی که مرورگر قرار است بفرستد.

 

 
 
هدرهای پیش‌بررسی به‌صورت خودکار ساخته می‌شوند: Origin، Access-Control-Request-Method و در صورت نیاز Access-Control-Request-Headers. لازم نیست آن‌ها را دستی در بخش هدرها وارد کنی.
